# 工作范围与交付证据

从目标仓库的项目指令、贡献指南、构建配置、现有测试和 CI 确定约束。说明规则来源；代码中观察到的惯例只是推断，规范缺失时提出具体建议，不顺手创建一整套治理文件。

开始前记录工作区与用户已有修改；保留它们，不重置、覆盖或打包进自己的修复。分析与评审请求保持只读；修复请求已授权的代码和必要测试直接完成。提交、推送、部署、应用数据库变更遵循会话中已有授权，不重复索要已给出的确认。未知生产副作用不能由本地修复授权推导。

只读评估需要执行验证时，可使用隔离副本或现有测试输出目录生成构建产物，保持源码、配置和用户文件不变。验证工具故障后，已有授权范围内可尝试可用的现有工具，并分别记录初次失败与重试结果。

交付通常留在会话中；需要持久化时使用目标仓库已有位置。按任务规模给出：

- 修改或发现 → 对应问题、证据位置、影响。
- 验证 → 命令、执行目录、退出码、断言或测试数量、产物位置。
- 状态 → **通过**（实际执行且相关断言成立）、**失败**（观察到不符合预期）、**环境阻塞**（工具、权限或依赖不可用）、**未验证**（未执行或证据不足）。
- 残余风险 → 哪些边界未覆盖，以及可执行的下一步。

测试命令退出 0 但发现零个测试，不构成测试通过；还原失败、工具超时、跳过测试、空测试工程也不能作为通过证据。静态阅读不能证明运行时行为。历史失败单独记录，不降低断言、删除测试、关闭检查或清空企业包源来换取绿色结果。

保存测试进程本身的退出码。使用 tail、grep 或 tee 截取日志时，不能把管道末端工具的退出码报告为测试退出码；使用 pipefail/PIPESTATUS，或先将命令输出保存到日志并立即记录退出码，再展示摘要。有限用例、静态等价性推断和实际执行过的边界分开说明。

优先验证受影响路径和已有契约，再按实际风险扩大范围。不要为单纯措辞或无行为影响的改动制造镜像测试；为缺陷回归、外部契约和有代表性的边界编写能发现错误的测试。
