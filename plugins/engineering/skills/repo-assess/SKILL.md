# 理解存量代码库

先读取[工作范围与交付证据](../../references/evidence.md)。默认只读；用户同时要求修复时，先明确已识别问题与修改边界，再完成所授权修复。

从真实执行入口建立证据地图：

1. 找到构建、启动、测试与 CI 的入口及所需服务，先列出准确的工作目录和命令，再在可用环境中执行有代表性的检查。不要把 README 命令未经核实当作已通过。
2. 沿一个关键业务请求或后台任务追踪入口、业务逻辑、持久化/外部调用和测试。给出文件位置与调用关系；多项目解决方案区分目录组织、声明依赖和实际生效的依赖。
3. 核对项目明示约束与代码现状：高影响行为是否有测试、故障是否可定位、配置/凭据如何注入、交付和恢复有哪些证据。只报告与任务有关的问题。
4. 按影响、发生条件、证据强度与修复成本排序。每个风险附具体场景、代码/配置位置和可执行的下一步；文件长度、目录数量或个人风格不是缺陷证据。

对候选风险检查反证，包括现有消费者、框架保护和测试。若影响依赖尚未见到的客户端或部署形态，标明假设与待验证条件；不能仅凭表示形式不同就断言存在兼容性故障。

交付前用文件搜索或读取工具核对报告中的实际文件路径和关键行，避免将类型名当成文件名。对依赖框架行为的风险，检查当前版本的实现、官方资料或针对性实验；尚未核实是否已有保护的推测放入证据缺口，不列入优先修复项。

.NET 项目按需读取[存量项目验证](../../references/dotnet.md)。其他技术栈使用其现有工具链。

输出简明的入口/依赖地图、验证结果、优先处理事项和证据缺口。没有源码、目标目录不明确或服务缺失时，先完成独立可做的部分，只询问阻碍结论的信息；不要推断不存在的业务架构。
