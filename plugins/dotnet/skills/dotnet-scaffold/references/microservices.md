# 服务组织

用户只说“微服务项目”时必须先确认：单个独立服务，还是多服务代码库。范围未定时仅询问，不先给出多服务推荐方案。多服务还需名称与职责；不默认生成订单、库存、支付等演示系统。Docker Compose 仅在选择多服务容器编排后才是默认工具，不是微服务的默认能力。

## 单个服务

保持标准 `src/<Name>/` 或用户指定的内部架构。HTTP 服务用 Web API；只处理后台任务可用 Worker。具备配置、内置日志和适用的健康检查。每个服务有独立运行/发布入口，但 Docker、数据库、网关和消息队列均需按需启用。

## 多服务

```text
services/
  ServiceA/src/ServiceA.Api/
  ServiceB/src/ServiceB.Api/
```

复杂服务可在自己的 src 下加入 Domain/Application/Infrastructure。测试在对应服务的 tests 下。根解决方案作为开发入口，不成为服务唯一构建入口。

- 各服务可直接对宿主 csproj restore/build/publish；可共享仓库级 SDK/CPM 约定。
- 服务之间不引用对方的实现项目；不默认创建共享 Domain、共享数据库或 SharedKernel。
- 明确本地端口且互不冲突；服务地址通过配置注入，不硬编码部署机器地址。
- 没有协作需求时不制造服务间调用。有需求才选择 HTTP、gRPC 或消息，并确认契约与超时。
- 启用容器编排时默认 Docker Compose。显式指定 Aspire 等工具时使用该工具并检查安装条件，不同时生成两套重复入口。

共享根 CPM/props 的服务在 Docker 中需要把这些文件带入 build context；所谓独立构建不代表可以遗漏必要配置单独复制一个 csproj。不得跨服务复制实现程序集来绕过边界。

分别构建并同时启动服务，验证端口、健康端点、配置地址及实际选择的通信。发布测试按服务执行；停止本次启动的进程，不按进程名批量终止用户已有服务。
